# TutinGuard — умная система пожарной безопасности (Хакатон 2026, кейс 2)

«Түтін» по-казахски — дым: система замечает дым раньше человека.

3D-симулятор офиса с датчиками отправляет данные на бэкенд, бэкенд превращает их в инциденты, а приложение оператора показывает
место тревоги на плане, ведёт журнал действий, задачи техника и сопровождает (смоделированный) выезд пожарной бригады.
**Все данные тестовые; демо не заменяет штатную сигнализацию и не отправляет реальные вызовы экстренным службам.**

```
 3D-симулятор (/sim/)  ──WebSocket /ws/ingest──▶  backend (FastAPI)  ──▶  PostgreSQL 16
   датчики, люди, огонь,  ◀── команды: сирены, эвакуация, ────┘    │
   пожарная бригада (DEMO)     «бригада выехала» (DEMO)            └──WebSocket /ws/ui──▶  приложение оператора (/app/)
```

## Запуск локально

Нужен Docker Desktop (или Docker Engine + compose plugin).

```bash
cp .env.example .env          # поменяйте POSTGRES_PASSWORD (только буквы и цифры)
docker compose up -d --build
docker compose exec backend python -m app.smoke_test   # самопроверка, должно быть «ИТОГ: всё работает»
```

- Приложение оператора: http://localhost:8000/ (вход: `operator` / `responsible` / `technician` / `admin`, пароль `demo` — меняется `DEMO_PASSWORD` в `.env`)
- 3D-симулятор: http://localhost:8000/sim/ — слева сверху должно быть «Сервер TutinGuard: подключено»
- API и документация: http://localhost:8000/docs
- Просмотр БД (по желанию): `docker compose --profile debug up -d` → http://localhost:8081 (сервер `db`, логин/пароль из `.env`)

Логи: `docker compose logs -f backend`. Остановить: `docker compose down` (данные БД сохраняются в volume `pgdata`; удалить их — `docker compose down -v`).

## Развёртывание на сервере

1. Купите/возьмите домен и направьте A-запись на IP сервера (например `tutinguard.example.kz`).
2. На сервере (Ubuntu): установите Docker, скопируйте папку проекта (`git clone` или `scp -r`).
3. `cp .env.example .env`, задайте сильный `POSTGRES_PASSWORD`, `DOMAIN=ваш домен`, `INGEST_TOKEN=случайная строка`.
4. `docker compose --profile https up -d --build` — Caddy сам получит HTTPS-сертификат Let's Encrypt (порты 80 и 443 должны быть открыты).
5. Откройте `https://ваш-домен/` и `https://ваш-домен/sim/?token=<INGEST_TOKEN>`. **Смените `DEMO_PASSWORD`** — иначе войти сможет любой, кто знает «demo».

Без домена (быстрый показ по IP): в `.env` поставьте `BACKEND_BIND=0.0.0.0` и запускайте без профиля — будет `http://IP:8000`.
База данных наружу не публикуется ни в одном варианте. API закрыт логином (токен на 72 ч); WebSocket симулятора — `INGEST_TOKEN`.

## Что умеет (функции кейса)

| Функция кейса | Где |
|---|---|
| 1. Регистрация объектов и зон | раздел «Объекты и зоны»: объект → зоны рисуются мышью на плане → датчики ставятся кликом; API `POST /api/sites`, `/api/sites/{id}/zones`, `/api/devices` |
| 2. Приём сигналов дыма/температуры | `WS /ws/ingest`: `telemetry` каждые 2 с, `event` при смене состояния, проверка по схеме (pydantic) |
| 3. Место тревоги, ответственный, журнал | зона подсвечивается на плане, баннер тревоги; инцидент `new → acknowledged → assigned → checking → closed` с обязательным результатом; журнал действий + выгрузка CSV |
| Повторные сигналы | сигнал из той же зоны увеличивает `repeat_count`, а не создаёт дубль; 2 датчика → «пожар подтверждён» |
| 4. Устройства без связи | нет `telemetry`/`heartbeat` дольше `OFFLINE_SECONDS` → «нет связи», инцидент и задача технику |
| 5. Проверки и ремонт | `inspections` (2 просроченные в демо), `repair_tasks`; 3 ложных срабатывания → датчик «подозрительный» |
| Эскалация | пожар не принят за `ESCALATE_SECONDS` → `siren_on` + `evacuation_on` и автоматический вызов бригады (DEMO) |
| Роли | дежурный оператор, ответственный сотрудник, техник (+ админ): разные меню и права, проверка на бэкенде (403) |
| Вызов пожарных (DEMO) | кнопка «🚒 Вызвать 101» в инциденте или автоэскалация → карточка вызова, в 3D приезжает машина, бригада тушит очаг; статусы «в пути → прибыли → тушение → ликвидирован» возвращаются в инцидент |
| Отчёты | реакция (медиана, 90%), инциденты по дням/типам/зонам/результатам, «шумные» датчики, CSV для Excel |

Формат сообщений — раздел 5 документа команды (`schema: "1.0"`). Дополнительно: `hello` (симулятор регистрирует зоны и датчики) и `ack` (ответ на команду).

## AI-прогноз возгорания

Многие пожары развиваются часами: греется розетка или кабель, тлеет изоляция, деградируют аккумуляторы ИБП, медленно течёт газ.
Обычный датчик молчит, пока не превышен порог. Модуль прогноза каждые 5 с оценивает по каждой зоне **вероятность возгорания в ближайшие 60 минут**
по слабым, но устойчивым признакам: темп роста температуры за 15/60/120 мин, ускорение роста, рост CO, «следы» дыма ниже порога, накопление газа.

- Модель: градиентный бустинг (scikit-learn), 38 признаков, окно 150 мин. Код: `backend/app/ai/`.
- Обучение: `python -m app.ai.train` (выполняется автоматически при `docker compose build`, ~2 мин). Карточка модели — `GET /api/ai/model`.
- **Данные синтетические**: 6-часовые эпизоды — норма и бытовые помехи (готовка, пар чайника, обогреватель, пыль, нагрузка серверов, курильщик)
  и медленные предвестники (перегрев розетки/кабеля, тление, тепловой разгон АКБ, утечка газа). На реальных пожарах модель не проверялась.
- Качество на отложенных эпизодах: ROC-AUC ≈0.96; предупреждает в ~77% случаев медленного развития, медиана упреждения ~53 мин;
  ложных прогнозов ≈0.1 на зону в сутки. Пропуски — в основном зоны без датчиков температуры/CO: по одному дыму предсказывать трудно,
  поэтому в опенспейсе и кабинете директора добавлены мультисенсоры (дым + температура + CO).
- Прогноз — **подсказка оператору**, он не заменяет и не отменяет штатную тревогу. Высокий риск ≥5 мин → инцидент «AI-прогноз» с причинами и
  советом; если в зоне затем случается пожар, в журнале фиксируется, за сколько минут его предупредил прогноз (`GET /api/forecasts`).
- API: `GET /api/risk` (текущий риск по зонам), `GET /api/risk/history?zone_id=dir`, `GET /api/forecasts`; живые обновления — сообщения `risk` в `/ws/ui`.

Демо: в 3D-сцене поставьте скорость **×60** (1 секунда = 1 минута) и запустите «7 · Розетка обогревателя» или «8 · Аккумуляторы ИБП».
Через 1–1,5 минуты пол зоны начнёт светиться оранжевым, в приложении появится «AI-прогноз» с причинами — примерно за час до срабатывания датчиков.
Для контраста — «5 · Микроволновка»: дым есть, прогноза нет.

## Звук и речевое оповещение

Кнопка **🔊 Звук** есть в 3D-сцене и в приложении оператора. Браузер включает звук только после первого клика по странице.

**3D-сцена.** Звуковые эффекты синтезируются в браузере (Web Audio, `frontend/sim/sound.js`), поэтому файлы для них не нужны: сирена-оповещатель, писк извещателя при сработке, треск огня, шипение при тлении и утечке газа, искры, щелчок замков выходов, шаги эвакуирующихся, фон офиса. Источники звучат тем громче, чем ближе к ним камера.

**Речевое оповещение СОУЭ.** Голосовые файлы лежат в `frontend/sim/sounds/`:

| Файл | Когда звучит |
|---|---|
| `voice_evac_kz.mp3` + `voice_evac_ru.mp3` | пожар и сирены: по кругу, сначала казахский, потом русский; сирена на это время приглушается |
| `voice_gas_ru.mp3` | утечка газа |
| `voice_test_ru.mp3` | команда «Тест оповещения» |
| `voice_allclear_ru.mp3` | «Сброс» после тревоги (отбой) |

Чтобы заменить голос, положите файл с тем же именем. Казахские версии для газа, теста и отбоя можно добавить в список `VOICE` в начале `sound.js`.

**Приложение оператора.** Звучат разные сигналы для пожара или газа (повторяется, пока оператор не нажмёт «Принять»), «внимания», AI-прогноза, потери связи, автоэскалации и закрытия инцидента. Голос браузера (ru-RU) коротко называет событие и зону.

## Приложение оператора (/app/)

Без сборки: `frontend/app/index.html`, `app.css`, `app.js` (чистый JS). Разделы зависят от роли:

| Раздел | Кто видит | Что там |
|---|---|---|
| Обзор | оператор, ответственный | KPI, план с местом тревоги и людьми, активные инциденты с кнопками, управление оповещением, AI-риск, лента событий |
| Инциденты | оператор, ответственный | таблица с фильтрами; карточка инцидента: хронология, датчики, карточка 101 (DEMO), этапы бригады |
| План объекта | все | зоны, датчики (клик — график показаний), люди, пожарная машина на улице |
| Устройства | все | состояние, показания, связь, срок проверки, ложные срабатывания |
| Обслуживание | техник, ответственный | задачи на ремонт, плановые проверки (просроченные — красным), «Выполнено» |
| AI-прогноз | оператор, ответственный | риск по зонам с причинами, история прогнозов и упреждение |
| Журнал / Отчёты | все / оператор, ответственный | события и действия, отчёты за 1/7/30 дней, CSV |
| Объекты и зоны | ответственный, админ | реестр объектов, редактор плана |

API для своего фронтенда: вход `POST /api/auth/login` → `{token}`, дальше заголовок `Authorization: Bearer <token>`;
живые обновления `WS /ws/ui?token=<token>` (`{type, data}`: `device`, `telemetry`, `incident`, `event`, `occupant`, `repair_task`,
`inspection`, `command`, `call_101_demo`, `risk`, `sim_status`, `site_changed`). Полный список — http://localhost:8000/docs.

## Пожарная бригада (DEMO)

Реальный вызов **никогда не отправляется**: карточка 101 формируется и показывается, а бригада моделируется в 3D.
`POST /api/incidents/{id}/dispatch` → команда `dispatch_brigade` в симулятор → машина едет `BRIGADE_ETA_S` секунд симуляции
(по умолчанию 45; в реальном городе норматив — до 10 мин) → бригада из 4 человек прокладывает рукав и тушит очаг → симулятор
присылает `brigade` со статусами `en_route / arrived / attack / extinguished / returning`, они попадают в журнал инцидента.
Без сервера сцена вызывает бригаду сама через 15 с после подтверждения пожара; есть и кнопка «🚒 Вызвать пожарных (DEMO)».
`AUTO_DISPATCH=escalation` (по умолчанию) — авто-вызов при эскалации, `confirmed` — сразу при подтверждении пожара, `off` — только вручную.

## Структура

```
backend/app/main.py     FastAPI: WebSocket, REST (вход, объекты/зоны/датчики, инциденты, отчёты, CSV), фоновые проверки
backend/app/auth.py     вход, токены, роли
backend/app/logic.py    правила: инциденты, повторы, подтверждение, эскалация, ложные срабатывания
backend/app/db.py       таблицы (SQLAlchemy 2.0)
backend/app/schemas.py  контракт сообщений v1.0
backend/app/smoke_test.py  самопроверка
backend/app/ai/         AI-прогноз: генератор данных, признаки, обучение, предсказание
backend/seed/site.json  демо-объект: 6 зон, 21 устройство (2 мультисенсора)
frontend/sim/           3D-симулятор (Three.js r160 лежит в vendor/, интернет не нужен)
frontend/app/           приложение оператора (вход по ролям)
deploy/Caddyfile        HTTPS-прокси для сервера
```

Разработка без Docker: `cd backend && pip install -r requirements.txt && STATIC_DIR=../frontend uvicorn app.main:app --reload` (без `DATABASE_URL` используется SQLite-файл).

## Сценарий демо (3–4 минуты)

1. Два окна: приложение (вход `operator`) и 3D-сцена `/sim/`. Включите звук в обоих.
2. В сцене запустите «1 · Удлинитель под столами». Через ~1 мин — «Внимание», затем «ПОЖАР подтверждён» двумя датчиками:
   красный баннер, зона горит на плане, голосовое оповещение СОУЭ (каз./рус.), люди эвакуируются к месту сбора.
3. В приложении «Принять» → «🚒 Вызвать 101 (DEMO)» → карточка вызова. В 3D приезжает пожарная машина, бригада тушит очаг,
   этапы появляются в инциденте. Закройте инцидент с результатом «Пожар подтверждён» — реакция и время прибытия попадут в отчёт.
4. Покажите автоэскалацию: запустите другой очаг и не принимайте тревогу 60 с.
5. AI: скорость ×60, сценарий «7 · Розетка обогревателя» — прогноз примерно за час до срабатывания датчиков.
6. Войдите техником: задача «нет связи» (кликните по датчику в сцене, чтобы оборвать связь) и просроченные проверки.
